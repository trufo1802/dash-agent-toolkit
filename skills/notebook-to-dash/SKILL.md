name: notebook-to-dash
description: Convert a Jupyter notebook (pandas/numpy/matplotlib/seaborn .ipynb analysis, including notebooks that plot through a project helper library such as fv.plot_*) into a Dash page whose numbers provably match the notebook, whose figures provably carry the same visual encodings (axes, colors, fills, labels, titles, layout), and whose build honors every explicit instruction. Use when asked to "make a dash page/dashboard from this notebook", "adopt/replicate my matplotlib plots in dash", port .ipynb analysis to an app, when numbers differ between page and notebook ("dashboard values don't match", "app shows different numbers than jupyter"), or when the page LOOKS wrong versus the notebook ("doesn't look like my notebook", "all dots are blue", "secondary axis/fill/second title line missing", "legend overlaps the title", "panels squashed", "table colors wrong"). Enforces a numeric parity gate (golden outputs), a visual parity gate (golden figure specs + layout lint + contact sheet) and an instruction-fidelity ledger before any UI work. A Dash app that is broken or slow is dash-fix; a chart edit with no notebook behind it is graph.

# notebook-to-dash

Why conversions fail, in order of damage:
1. **Silent numeric drift** — the agent rewrites the computation freehand while restructuring for callbacks; a changed `dropna`, resample rule, ddof, or join direction shifts every downstream number. Nothing errors. The user finds it by eye.
2. **Dropped explicit instructions** — the agent exercises discretion on the WHOLE prompt instead of only its gaps; stated requirements get averaged away with the vibes.
3. **Presentation reinvented** — the notebook cell is one line (`fv.plot_df_subplots(dfs, axis=["L1","R1"], threshold_fill=[0,None], title_last_yymmdd=True)`); the figure's definition is the 300-line helper behind it. The agent ports the call site, redraws "a dashboard" from the rendered image plus the house palette, and the secondary axis, the green/red fills, the per-point colors and the second title line vanish without an error. Then matplotlib's automatic layout (tight_layout, figsize growing with rows) is replaced by Plotly's fixed margins, so legends sit on subplot titles and twelve panels share 450 px. Each round-trip with the user fixes one of these; a gate finds all of them at once.

All three have mechanical fixes. The notebook is executable ground truth — its numbers AND its figures; the prompt is a contract. Treat them that way.

## Iron rules

- **Transplant, don't transcribe.** Compute lines move VERBATIM from notebook cells into pure functions. Only two boundaries may change: data loading (notebook I/O → the app's data layer) and the plotting LIBRARY (matplotlib/seaborn → Plotly). Changing the library does not license changing the ENCODING: axis assignment, per-series and per-point color, fills, reference lines, text labels, title lines, scales and fixed limits are requirements with the same status as a number. Every line you DID change gets listed in the parity report.
- **Port the helper, not the cell.** When the notebook plots through project helpers (any `module.plot_*` / `color_table`-style call — inventory with `templates/plot_calls.py nb.ipynb --receiver fv`), the unit of port is the helper: a Plotly twin with the same name, signature and kwarg semantics, written from the helper's SOURCE, with every kwarg the notebook passes either handled or raising `NotImplementedError` — never ignored. The page calls the twin with the notebook cell's arguments verbatim. Notebooks that plot inline (`ax.plot` in cells) port cell by cell through `reference/mpl_plotly_map.md`.
- **No UI before both gates are green.** Ported compute must reproduce the notebook's golden outputs (Step 3) and ported figures must reproduce the notebook figures' structure and layout (Step 4). A beautiful page with wrong numbers, or right numbers under the wrong picture, is worse than no page.
- **Discretion only in the gaps.** Explicit instructions are load-bearing; fill unspecified areas with judgment and FLAG each judgment. Never trade an explicit ask for a "better idea" silently — propose, don't substitute. The host palette/theme applies to page chrome, and to figure colors only where the notebook used defaults and color carries no meaning — as a ledgered `[I#]`, never by default.
- **The notebook is the page's default state.** Interactivity is additive: with default control values, the page must show exactly what the notebook shows. New knobs extend; they never redefine.

## Procedure

### Step 0 — Requirements ledger (before reading any code)
From the user's prompt AND notebook markdown cells, extract a numbered ledger:
- `[E#] explicit` — stated requirements, quoted verbatim. Zero discretion.
- `[I#] inferred` — gaps you will fill; note the choice you intend.
- `[C#] control` — helper kwargs the user wants exposed as page controls (`threshold_fill → dropdown per DataFrame`, `legend → dropdown`, `ncols → dropdown`, `recompute → button`). Options come from the helper's accepted values (type hints, docstring, the branches that read the kwarg) — never invented; the default is the notebook cell's value. A named kwarg without options = ONE question, not a guess.
If an explicit item is ambiguous enough to change the numbers or the layout materially, ask ONE focused question now — a wrong guess costs a full rebuild.

Then classify the notebook's **archetype** — it decides what "the page" even means:
- **Linear analysis** (load → transform → figures): one page mirroring it top-to-bottom. The common case; the rest of this skill reads naturally.
- **Library + examples** (cells defining a function library + many demo calls): the compute layer is the library cells transplanted verbatim — the porting work is already half done; the PAGE is one control-driven view whose control defaults reproduce ONE designated example. Ask which example is the flagship, or pick and flag `[I#]`. Simulation/validation/assert cells → `dropped (notebook-only validation)` in the coverage map — but harvest their asserts as goldens (Step 1).
- **Report** (mostly markdown + a few figures): static layout, no controls; the parity gate applies unchanged.
And its **plotting style** from the `plot_calls.py` receiver column: helper-driven (`fv.*`, any project module) → twin rule; inline (`ax`/`plt`/`df.plot`) → per-cell translation. Mixed is common; label each figure cell.

### Step 1 — Harvest golden outputs
The `.ipynb` JSON already stores executed outputs — harvest without re-running when outputs are present and the notebook looks linearly executed (execution_counts monotonic). Use `templates/extract_goldens.py`: per code cell → source + stream/execute_result text. Collect as goldens:
- every printed/displayed scalar and small table,
- shapes + a few exact cells of key DataFrames,
- for each figure: WHAT is plotted — series names, transforms, axis assignment, scale (log?), groupby keys (read the plotting cell's source, not the rendered image) — and, in Step 4, a structural figure spec captured from the same inputs.
If outputs are missing/stale or execution order is suspect, execute headless first (`jupyter nbconvert --to notebook --execute`) in an env matching the notebook's — pandas MAJOR version drift between notebook env and app env is itself a numbers-change source; pin or verify. (Field note: quant notebooks are commonly saved with outputs STRIPPED — expect the re-execute branch to be the normal path, not the exception.)
**When re-execution disagrees with stored outputs, STOP.** The user approved the STORED numbers; re-executed values may differ (hidden state, data updated since, env drift). Diff them; on any divergence ask ONE question — "notebook shows X, clean re-run gives Y: which is the truth to match?" — and record the answer in the ledger. Silently goldening re-executed values means "provably matching" a notebook the user has never seen.
**Goldens must originate from the NOTEBOOK** — stored outputs or an nbconvert re-execution of the .ipynb — never from the ported module. Asserting the port against values the port itself produced is circular and permanently green. `goldens.json` (and any golden parquet) exists on disk BEFORE the first line of ported code is written.
CAUTION: displayed values are ROUNDED for display. Golden comparisons against parsed display text need tolerance (`rtol` matched to printed precision); re-executed in-memory values allow exact comparison.
**In-notebook asserts are premium goldens.** If the notebook self-verifies (assert cells, planted ground truth, identity checks), reproduce those asserts in the parity suite CALLING THE PORTED MODULE — exact, semantic, immune to display rounding. Rank them above anything parsed from output text.
**Moving inputs (API fetches, "last N days" slices, DB queries that update daily):** goldens against live inputs go red tomorrow by design — that red says nothing about the port. Freeze: snapshot the notebook's exact inputs to a file at harvest time (parquet/CSV, as-of date in the filename); both parity gates run on the SNAPSHOT forever. The page's live path is covered by loader parity on SCHEMA (shape, dtypes, column set, index monotonicity/tz) rather than values. Any `today`/`tail(N)` anchoring in the compute becomes an explicit parameter — snapshot's as-of date in the gate, live today in the app — with a ledger entry.

### Step 2 — Port compute into a pure layer
One module, no Dash imports (mirror the app's layer rules: compute ≙ services/plotting layer). Functions take data in, return DataFrames/Series/scalars. Cell-to-function mapping stays 1:1 where possible. Anything a plotting helper COMPUTES before drawing — threshold clipping for fills, regression coefficients, equalized limits, "last valid date" strings — belongs here, parity-tested, not inside the twin. Keep a **cell coverage map**: every notebook code cell → `ported to <func>` | `dropped (<reason>)` | `deferred (<reason>)`. Silent omission of a cell is how "key instructions" vanish — the map makes omission a visible decision.

### Step 3 — NUMERIC PARITY GATE (mandatory, blocking)
Write the parity test from `templates/test_parity.py`: run ported functions on the SAME inputs the notebook used; assert against goldens (`assert_frame_equal`, `np.allclose` with stated tolerances; check index alignment, dtypes, tz). Run it. Red = fix the port, not the tolerance. State every tolerance and why. Only a green run unlocks Step 4.
**Loader parity is part of the gate.** The data-loading boundary is the one place the skill PERMITS a rewrite — so it gets its own check: the APP data layer's output vs the frame the NOTEBOOK loaded (shape, index min/max, dtypes, N spot values). Compute parity against the notebook's CSV while the app silently loads a different date range / adjusted series from its DB is the classic way every number ends up wrong with a green gate.
Common drift sources to check when red: dropna/fillna defaults, `ddof` (pandas std=1, numpy std=0), resample rule + label/closed, merge how= + duplicated keys, sort stability, groupby observed=, pct_change fill_method, datetime tz/normalization, seeds.

### Step 4 — VISUAL PARITY GATE (mandatory, blocking)
Per notebook figure cell, from `templates/test_visual_parity.py` (helpers in `templates/fig_spec.py`, `templates/layout_lint.py`):
1. **Golden spec.** `capture_mpl(helper, *cell_args)` headless in the notebook's env on the Step-1 snapshot → `mpl_spec(fig)` → `goldens/golden_fig_<cell>.json`. From the NOTEBOOK helper only; a spec taken from the twin is circular.
2. **Structure.** `plotly_spec(twin(*cell_args))`, then `diff_spec(golden, got)` → zero `ERR` (panel count, title lines, secondary axes, line count and colors per side, fill colors, marker points and distinct colors, h/v lines, texts, scale). `WARN`s are judged and ledgered. `colors=False` only when the user chose the host palette on record.
   **Control parity.** The twin shares the helper's signature, so every `[C#]` has an oracle: capture one extra golden from the mpl helper at a NON-default value per control (`capture_mpl(helper, *args, **{**cell_kwargs, kw: alt})`) and diff the twin at the same value. Fills appear when `threshold_fill` is set, a right axis appears when a tag flips to `R1` — proven, not assumed.
3. **Layout.** Every twin builds its geometry through ONE `layout_policy(nrows, ncols, title_lines, legend, ...)` — height from rows, margins from title lines, legend placement — instead of per-figure numbers; `lint_layout(fig)` (no browser) → zero `ERR`. Step 7 adds `overlaps_in_page()` on the rendered Graph.
4. **Eyes.** `contact_sheet(mpl_fig, plotly_fig, png)` — notebook left, port right. Read the PNG. The spec encodes structure; the sheet shows what it does not (line widths, label collisions, date formats).
Construct mapping: `reference/mpl_plotly_map.md` (table + number-changing traps) and `reference/visual_parity.md` (helper-twin contract; recipes for twinx grids, threshold fills, two-line titles, per-point colored scatters, regression panels, Styler tables, title collisions, panel height; failure table). Red = fix the twin, never the golden. Only a green run unlocks Step 5.

### Step 5 — Assemble the page
Now Dash: layout, controls, callbacks — controls' DEFAULT values = the notebook's parameter values. Follow the host app's conventions (figure factories, layer rules, uirevision) — if the repo has agent docs (CLAUDE.md/AGENTS.md), they win on style, within the encoding rule above. `dcc.Graph` height equals the figure's `layout.height` (set `style={"height": ...}` as well); section headings live in the page (`html.H4`), not in `layout.title`, when the figure already has subplot titles.
**Iron rule for callbacks: zero compute expressions in callback bodies.** Callbacks may only CALL functions from the parity-tested modules — a freehand `df[df.date >= start].std()` inside a callback reintroduces the drift the gate just eliminated, with ddof/dropna choices made a second time. If a control needs a new computation, add it to the compute module and extend the parity test (at least one assertion at a NON-default control value, so interactivity paths are covered, not just the notebook's defaults).
**`[C#]` controls pass straight through.** Callback body = `twin(*data, **{**NOTEBOOK_KWARGS, **control_values})`; the twin is the only place a kwarg is interpreted. Widget by kind (host component library wins): enum/`Literal` → dropdown; bool → switch; per-DataFrame list kwargs (`axis`, `threshold_fill`, `color`) → one dropdown per DataFrame labelled by `dfs_name`; actions → button; always a "reset to notebook" button. Kwargs that change the DATA (date range, universe, window) are compute arguments: they route through the compute module with a non-default numeric assertion, and key the axis-level `uirevision` (dash-gotchas-review P6). `reference/visual_parity.md` §6 has the mapping and the callback pattern.
**Runtime triage per ported function — measure, don't guess.** Time each on realistic data, then route: **interactive** (≲1s: callable per control change), **precompute** (slow batch — grid searches, walk-forward sweeps, heavy fits → a generation script writing a parquet artifact the page loads; the script lives next to the page and its outputs are parity-tested like any compute), **exclude** (research-only cells → coverage map `dropped (offline analysis)`). A page that reruns a five-minute cell on every slider tick fails as surely as one with wrong numbers; a page that silently swaps the slow exact method for a fast approximation fails worse — that swap is a ledger item, never a default.

### Step 6 — Fidelity walk (before reporting done)
Walk the ledger item by item: `[E1] <quote> → implemented at <file:line/place>, verified by <parity test / screenshot / value>`. Any `[E#]` not implemented = say so explicitly and why — never silently. List every `[I#]` judgment made, and every `[C#]` as `kwarg → widget, options, default, non-default parity test name`. Attach the cell coverage map and, per figure cell, the golden spec file, the diff result and the contact sheet path. This walk IS the deliverable's receipt; a conversion without it is unreviewable.

### Step 7 — Verify in the browser
Hand off to `dash-ui-verify` (or the repo's harness): page renders, key numbers visible on the page spot-match goldens, controls at defaults reproduce the notebook, `overlaps_in_page(page, "#<graph-id>")` returns no legend/title/annotation intersections for every Graph. Screenshot for the visual claim.

## Output contract

End with a **PARITY REPORT** block: the LITERAL pytest commands and result lines for BOTH gates (`12 passed in 3.1s`) as the receipt — "N checks green" without the command output is an unverifiable claim; tolerances with justification; per figure cell: `ERR 0`, WARNs with their ledger items, lint result, sheet path, overlap check; lines changed vs notebook (the two boundaries only, or justified); cell coverage map; fidelity walk (E-items with evidence, I-judgments); deviations. If the user asked for it as a file, write `PARITY.md` next to the page module.

## When the page later "doesn't match"

Regression path: re-run both parity tests first. Branches:
- **Red numeric parity** = compute drifted (env change, edited function).
- **Red visual parity** = twin drifted (edited twin, plotly major bump, policy change).
- **Green both + wrong page**: check the DATA LAYER first (app loader returning different range/adjustments/NaN handling than the parity inputs — re-run the loader-parity check), THEN the UI/callback layer (stale Store, wrong control default, transform applied twice, freehand compute in a callback body), THEN layout (`lint_layout`, `overlaps_in_page` — a CSS or container change can squash a figure the gate still passes).
The tests bisect the search space in one run — that's why they stay in the repo, not in the chat.
